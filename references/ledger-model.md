# 账本模型与计算口径

## 一、统一事件模型

所有来源都归一成同一种结构，后续分流 / 聚合 / 分类 / 对账只认它。

```python
@dataclass
class Txn:
    platform: str          # wechat | alipay
    occurred_at: str       # "YYYY-MM-DD HH:MM:SS"
    direction: str         # expense | income | neutral
    amount: float          # 元，两位小数
    counterparty: str      # 原始交易对方
    description: str       # 商品 / 商品说明
    txn_type: str          # 微信:交易类型  支付宝:交易分类
    category: str          # 产品类目
    status: str            # 当前状态 / 交易状态
    pay_method: str
    pay_kind: str          # cash | credit | balance | other
    external_id: str       # 交易单号 / 交易订单号（对账黄金主键）
    bucket: str            # ledger | neutral_flow | discarded | zero_amount
    needs_review: bool
```

`ledger.csv` 的输出列：
`平台, 时间, 收支, 金额, 类目, 类目来源, 置信度, 商户, 商品说明, 支付方式, 支付性质, 状态, 交易单号, 需确认`

## 二、四类口径（必须拆分）

| 口径 | 定义 | 是否计入 `收支` |
|---|---|---|
| **消费** | 真实花掉的钱。默认统计口径 | ✅ 计入 |
| **转账 · 人际** | 转账、红包、群收款、代付 —— 钱只是换了位置 | ✅ 计入 `收支`，但**默认从"消费"里剔除** |
| **投资** | 基金买入 / 卖出 / 收益 | ❌ 不计收支 |
| **信用还款** | 花呗 / 信用购还款 | ❌ 不计收支 |

类目 → 口径的映射：

```python
CLS = {"转账·人际": "transfer", "资金调拨": "transfer",
       "投资": "invest", "投资·收益": "invest",
       "信用·还款": "debt", "退款": "refund"}
# 其余一律 "consume"
```

**支付性质（`pay_kind`）独立于口径**，表达"钱从哪来"：

```python
CREDIT  = ("花呗", "信用购", "信用卡", "白条", "分期")   # 信用 → 负债
BALANCE = ("余额宝", "零钱", "零钱通", "账户余额")        # 余额类
CASH    = ("银行", "储蓄卡", "借记卡")                     # 现金类
```

## 三、分流算法

```
按 (收/支 × 交易状态) 四向分流：

  支出 / 收入 且非关闭     → bucket = ledger        （主账本）
  交易状态 ∈ {交易关闭,…}  → bucket = discarded     （剔除）
  金额 == 0                → bucket = zero_amount   （单列）
  收/支 == 不计收支/中性    → bucket = neutral_flow  （资金流水区，默认折叠）
```

**不可省略的两步：**

1. **退款配对**：`状态含"退款"` 或 `商品说明含"退款"` 的行，按（金额相同 + 说明互含）
   与原始交易配对 → 整对标记，从账本剔除（钱回来了）
2. **重复小额聚合**：按 `(交易对方, 商品说明)` 分组，组内 `>= 5 笔` 且金额高度一致
   → 折叠为一条"计划"（笔数 + 合计 + 区间）。实测数百笔固定金额定投可折叠成个位数分组

## 四、分类策略（两平台不对称）

| 平台 | 是否自带分类 | 策略 |
|---|---|---|
| 支付宝 | ✅ 19 类「交易分类」 | **类目映射为主**（`ALIPAY_CATEGORY_MAP`），商户知识库用于**纠错** |
| 微信 | ❌ 只有「交易类型」（形态，不是类目） | **完全依赖商户知识库 + 待确认队列** |

**注意：支付宝的分类是"高起点"而不是"免检"。** 实测错误例子（商户名已换成占位符）：

- `某个人收款码 / 收钱码收款` 被归为「交通出行」
- `某财经杂志 / 订阅年费` 被归为「日用百货」

**微信侧才是有真难度的地方** —— 商户名是马甲公司名，字面完全看不出：

```
<共享单车马甲公司A> / 先乘后付      → 共享单车
<共享单车马甲公司B> / 先乘车后付款  → 共享单车（同一业务，另一个马甲）
<智慧停车公司>      / 某车牌号包月  → 停车
```

> 上面是示例占位符。微信的商户名常是平台马甲公司，字面完全看不出业务 ——
> **这些名字来自具体账单，属于个人痕迹，不要写进随技能分发的文件**：
> 写进工作目录的 `merchant_kb.local.json`。

**微信「交易类型」可直接定类**（无需 AI）：
`转账` `微信红包` `微信红包（群红包）` `群收款` → `转账·人际`；
`转入零钱通-来自零钱` 等 → `资金调拨`。

**置信度分级**（决定是否进待确认队列）：

| 置信度 | 处理 |
|---|---|
| `>= 0.9` | 静默入库 |
| `0.7 ~ 0.9` | 入库 + 打"待确认"标记 |
| `< 0.7` | 进待确认队列，请用户一键确认；确认后**记住商户规则** |

## 五、核心指标计算

```
消费发生额      = Σ ledger 中 direction=expense 且 cls=consume
信用消费        = Σ 上述中 pay_kind=credit
推算现金流出    = 消费发生额 − 信用消费
信用还款        = Σ neutral_flow 中 cls=debt
投资买入/卖出   = Σ neutral_flow 中 cls=invest
净负债变化      = 信用还款 − 信用消费      （正 = 负债减少）
```

**双视角的意义**：消费发生额回答"花了多少"，现金流出回答"钱实际出去了多少"。
两者差异 = 信用消费。这是花呗用户最需要、也几乎没人算得清的一组数。

## 六、对账校验（回归测试合同）

解析器必须能**还原官方口径**。这是唯一的正确性保证：

| 平台 | 校验项 | 期望（不变量） | 还原方法 |
|---|---|---|---|
| 支付宝 | 总笔数 | = 解析到的明细行数 | 明细行数 |
| 支付宝 | 支出金额 | = 全部支出行金额 − 交易关闭金额 | 逐项差额为 0 |
| 支付宝 | 收入 | = 全部收入行合计 | 笔数与金额同时为 0 |
| 支付宝 | 不计收支 | = 全部不计收支行 − 桶内「买入退款」 | 逐项差额为 0 |
| 微信 | 支出 | = 全部支出行合计（无关闭/零金额） | 逐项差额为 0 |
| 微信 | 收入 | = 全部收入行合计 | 逐项差额为 0 |
| 微信 | 中性交易 | = `收/支 = /` 的行合计 | 逐项差额为 0 |

**判定标准是"逐项差异为 0"，不是"等于某个历史数字"。**
绝对金额随账单变化，写死具体数值会让校验在换账本后静默失效：
所以这里只写不变量。如果你手上有当时的样例账单，把它的数字填进本地笔记自查即可 ——
**不要把它写回本文件**（那是账单指纹）。

**改动解析逻辑后必须重跑这 7 项。**
