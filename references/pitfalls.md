# 已知的坑（全部为实测，含可复现的数字）

## 一、官方统计口径本身有 3 个坑 —— 不要拿它当校验真值

支付宝 preamble 自己写着：
> "6.因统计逻辑不同，明细金额直接累加后，可能会和下方统计金额不一致，**请以实际交易金额为准**。"

> 📌 本文所有金额都是**为讲清口径而构造的示例值**，不是任何真实账单的数字。
> 它们只保证"算式自洽"，不要拿去和你的账本比对。

### 坑 1：同一行统计里，笔数和金额口径不一致

```
官方「支出：120 笔 10000.00 元」（虚构示例值）
  笔数 120     = 全部支出行 120 笔（含「交易关闭」10 笔 + 零金额 2 笔）
  金额 10000.00 = 支出总额 12000.00 − 交易关闭部分 2000.00
```

**笔数含"交易关闭"，金额不含。** 所以想复现官方数字，必须对笔数/金额用两套规则。

### 坑 2：不计收支的差额是"桶内冲减"

```
全部不计收支行合计 = 合计A（假设 12,000.00）
官方              = 合计B（假设 11,000.00）
差 = 1,000.00  ← 应正好等于「基金买入退款」几笔之和（假设 500 + 500）

（这里所有数字都是构造的示例：真实差额取决于当时的退款笔数与金额。）
```

规则：
- **基金买入退款**：原「买入」也在不计收支桶里 → 退款必须在**桶内冲减**
- **消费类退款**（例如购物类、票务类各若干笔）：原支出在「支出」桶里 →
  跨桶抵消，所以**保留在不计收支里**

### 坑 3：微信的统计是干净的

```
官方：支出 120 笔 10000.00 / 收入 5 笔 2000.00 / 中性 1 笔 30.00  → 与明细逐项一致（虚构示例值）
```

微信账单没有「交易关闭」和零金额，所以笔数金额都直接对得上。

### 正确的校验方式

**以明细为准**，用"还原官方口径"来验证解析器，而不是把官方数字当 ground truth：

```python
# 支付宝支出：笔数用全部支出行，金额排除交易关闭
n_exp = len([t for t in txns if t.direction == "expense"])
amt_exp = sum(t.amount for t in txns if t.direction == "expense" and t.status not in CLOSED)
# 支付宝不计收支：笔数用全部不计收支行，金额减掉桶内「买入退款」
n_neu = len([t for t in txns if t.direction == "neutral"])
amt_neu = sum(t.amount for t in txns if t.direction == "neutral") - sum(
    t.amount for t in txns if t.direction == "neutral" and "买入退款" in t.description)
```

## 二、口径混淆：转账不是消费（最容易把产品做错）

实测某 3 个月账单：

```
「转账·人际」成为第一大"消费"类目，占全部支出约 45%
单月最严重：占该月全部支出约 39%
```

**若不拆分口径，该月"消费"会被虚报约 65%**（量级示意：4,181 → 6,887）。

> **必须把每一笔拆成四类：消费 / 转账 / 投资 / 还款。**
> 混在一起，「我这个月花了多少」这个问题在定义上就无解。

## 三、花呗：必须按权责发生制

实测某 3 个月：**信用消费（花呗/信用购）占真实消费约 38%**；
同期还款 3 期。

- 用花呗消费时**钱没出去**，现金流出发生在**下个月的还款日**
- 若按现金流记账：「这个月花了多少」永远是错的
- 正确做法：消费按**发生日**计入消费；还款标记为**负债偿还**，不计收支

## 四、其他必须处理的明细问题

| 问题 | 处理 |
|---|---|
| `交易关闭` | **剔除**（未完成的交易，官方金额统计也不含）|
| `退款成功` | 与原始支出**配对冲销**（实测成对出现，且原交易常为 `交易关闭`）|
| 金额 = 0 | 单列（实测是「医保支付(不含自费)」，有信息价值但不算支出）|
| 重复小额 | **必须聚合**：实测「投资理财」类目里绝大多数是每只基金每日 10.00 元定投 → 折叠成个位数分组 |
| 中性交易 | 微信 `收/支 = /`、支付宝 `不计收支` → 资金流水区，默认折叠 |

## 五、技术坑（踩过的）

| 坑 | 症状 | 正确做法 |
|---|---|---|
| **UID 当成序号** | `list`/`fetch` **静默返回空**，看起来像"邮件没附件" | `UID FETCH` 的响应里必须解析 `UID nnn`，`item[0]` 开头是**序号**不是 UID |
| RFC2047 折行 | 附件名乱码 | 用 `decode_header`；**不要**先 `re.sub(r"\s+","")`，会把 `?=` 和 `=?` 粘成 `?==?` |
| GBK 当 latin-1 | 中文附件名乱码 | `fn.encode("latin-1").decode("gbk")` 兜底 |
| imaplib 非 ASCII 搜索 | `SEARCH` 报错 | 用 `SINCE` 做粗筛，**中文关键词在本地用 Python 过滤** |
| ZipCrypto vs AES | 判断错加密方式导致用错工具 | `compress_type == 99` 才是 AES；`flag_bits & 0x40` 是 PKWARE 强加密 |
| 非交互环境提示密码 | 管道里 `getpass` **卡死** | 只在 `sys.stdin.isatty()` 时提示 |

## 六、加密与口令（合规相关，必读）

- 两个平台的账单 zip 都是 **ZipCrypto**（不是 AES）
- **解压口令每次都变**，由平台经**另一条通道**下发：
  - 微信 → 【微信支付】公众号消息
  - 支付宝 → 申请页面显示
- **ZipCrypto 的已知明文攻击（bkcrack）在此无意义** —— 因为口令是 6 位纯数字，
  **口令空间只有 10^6**，可直接穷举（实测约 16,000 次/秒 ≈ 60 秒）。

> ⚠️ **默认不要主动穷举口令。** 这是产品级决策，涉及平台协议与商店审核风险。
> 与用户明确确认后再做，并说明代价。**服务端绝不接触口令。**
